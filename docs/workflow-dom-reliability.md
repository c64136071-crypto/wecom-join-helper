# D-MAINT-2：提交回执与诊断截图隔离（未独立审查候选）

原应用/GUI、受限 JSON、固定 CLI、同一流程内核、持久预留和 Windows Job 清理边界不变。
本批仅处理一个实测缺陷：应用保存已经确认，但后续诊断截图超时使桥接器不发成功 ACK。
不进入 EXE/安装器制作或公开发布，不添加任意 URL/selector/shell，不操作真实公司业务。

## 已建立的因果范围

正常显示窗口的对照，通过延迟 750ms 的自有保存、真实 DOM receipt 和截图。
只最小化本批创建的 Chrome 窗口后，服务端已持久化 receipt=1，DOM receipt=1 已被桥接器
读取，页面身份也已复核；`page.screenshot` 随后在 5000ms 到期，旧行为返回 unknown。
真实回归先观察到 `(4, unknown)` 不等于期望 `(0, completed)`，再实施最小修复并通过。

这证明当前代码的“已确认回执后的截图超时耦合”缺陷；**不证明它是旧 d2 偶发失败的
唯一原因**。旧 d2、诊断和警告记录不删除、不改为成功，也不据此宣称 GPU 警告已消除。

## 最小修复

`workflow_dom_capture.cjs` 统一处理 save/export/input 完成后的诊断截图：

1. 使用原 5000ms 截图预算；仅捕获截图本身的 `TimeoutError`。
2. 记录固定 `diagnostic_screenshot_timeout` 事件，不记录异常文本、字段值、路径或 locator。
3. 无论截图成功或属于该超时，都再次校验当前页面身份后才能返回 ACK。

非超时错误、记录日志失败、身份变更继续失败；获取业务回执/下载的逻辑在捕获函数之外，
真正丢回执仍是 unknown。步骤/总预算、取消、审计 fsync、持久不重放均没有放宽。
如果截图占用了整个步骤预算，父执行器仍会按原规则拒绝过期 ACK，不保证所有超时都变成功。
启动时初始截图仍是原有启动门禁，不在本次改变范围。

截图是辅助证据：超时后 `final.png` 可能不存在或保留前一步内容，不应单凭它断言提交。
以实际应用 receipt、保存记录、下载字节和最终 CLI 返回为准；有截图 warning 不等于截图成功。
